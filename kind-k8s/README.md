# Local kind setup

Everything in this directory targets a local **kind** cluster. No Azure account, no AKS,
no Key Vault, no ACR.

## What differs from the AKS manifests

| Azure | Local |
|---|---|
| ACR images (`acrecommercedevt7o2q.azurecr.io/...`) | locally built `*:local`, loaded with `kind load` |
| Key Vault CSI + `SecretProviderClass` | plain Secrets generated by `scripts/create-secrets.sh` (never committed) |
| Workload Identity (`azure.workload.identity/*`) | removed — no webhook, no Entra ID |
| RBAC bound to an Entra group object id | bound to a `developer` ServiceAccount |
| Zone spread (`topology.kubernetes.io/zone`) | host spread, `ScheduleAnyway` |
| Azure LoadBalancer for ingress | `extraPortMappings` to host ports 80/443 |
| TLS via cert-manager + Let's Encrypt | plain HTTP (no public DNS name to validate) |

## 1. Build the images

From the repo root. These tags are what `base/*/​*_deployment.yaml` reference:

```bash
docker build -t user-service:local    ./services/user-service
docker build -t product-service:local ./services/product-service
docker build -t order-service:local   ./services/order-service
docker build -t aether-frontend:local ./frontend
```

No `--platform` needed: these run on your own machine's architecture, unlike AKS which
required `linux/amd64`.

## 2. Create the cluster

```bash
kind create cluster --name ecommerce-local --config kind-k8s/aks-k8s/kind-config.yaml
```

Delete an existing cluster first if you have one — port mappings cannot be added later:

```bash
kind delete cluster --name ecommerce-local
```

## 3. Load the images into the cluster

kind nodes are containers with their own image store. They cannot see your host's Docker
images, and there is no registry to pull from — so `ImagePullBackOff` here means you
skipped this step:

```bash
for img in user-service product-service order-service aether-frontend; do
  kind load docker-image $img:local --name ecommerce-local
done
```

Re-run this after every rebuild. `kind load` does **not** restart pods; follow it with
`kubectl rollout restart deployment/<name> -n ecommerce-dev`.

## 4. Install the ingress controller

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod --selector=app.kubernetes.io/component=controller \
  --timeout=180s
```

Use the **kind** provider manifest, not the cloud one — it uses a hostPort instead of a
LoadBalancer Service, which would sit `<pending>` forever.

Then turn on controller metrics — from ingress-nginx 1.15 `--enable-metrics` is **off by
default**, so without this the Ecommerce RED dashboard's ingress row is empty. Re-run
this after any re-apply of the manifest above, which removes the flag again:

```bash
kubectl patch deploy ingress-nginx-controller -n ingress-nginx --type=json -p='[
  {"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--enable-metrics=true"},
  {"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--metrics-per-host=false"}]'
kubectl apply -f kind-k8s/monitoring/ingress-nginx-metrics.yaml   # after the monitoring stack (step with kube-prometheus-stack)
```

And make rate-limited requests answer **429**, not ingress-nginx's default **503**. The shop
Ingress limits each client to 20 req/s (`base/ingress.yaml`); with the default, every
throttled request would look like an outage on the dashboards and in the error-rate SLO:

```bash
kubectl -n ingress-nginx patch configmap ingress-nginx-controller --type merge \
  -p '{"data":{"limit-req-status-code":"429","limit-conn-status-code":"429"}}'
```

## 5. Install metrics-server (needed by the HPAs)

kind ships without it, so `kubectl top` and every HPA report `<unknown>`:

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl patch deployment metrics-server -n kube-system --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
```

The patch is mandatory on kind: kubelets serve certificates signed by the cluster CA,
which metrics-server does not trust by default, and it crash-loops on TLS verification.

## 6. Deploy the app

```bash
kubectl apply -f kind-k8s/base/namespace.yaml
./kind-k8s/scripts/create-secrets.sh
kubectl apply -R -f kind-k8s/base/
```

Namespace first — everything else lives in it. Then the Secrets: the script generates a
random 64-character JWT signing key and an internal API token (for the service-to-service
`/internal` routes) and creates the three `*-service-secrets`. Nothing
secret is stored in the repo. (`base/secrets.yaml` used to hold the key in plaintext; it is
gone and git-ignored.) Every service **refuses to start** in production with a missing,
short or publicly known `JWT_SECRET`, so skipping this step shows up as a crash-loop with
that message in the log.

Rotate the key at any time (this signs every shopper out):

```bash
./kind-k8s/scripts/create-secrets.sh --rotate
kubectl -n ecommerce-dev rollout restart deploy/user-service deploy/order-service deploy/product-service
```

The namespace **enforces** Pod Security `restricted`: a pod without `runAsNonRoot`,
`allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]` and a `RuntimeDefault`
seccomp profile is rejected at admission.

NetworkPolicies (default-deny plus one rule per flow) are in `kind-k8s/security/`. They
are verified but **not kept enabled** on kind: under the k6 load, kindnet's NRI-based
enforcement drops out and blocks newly scaled pods. The file header has the details and
the ways to run them for real (Calico, AKS, more CPU).

Stock and reservations live in Redis (product-service). To restock a product by hand,
call the internal API from inside an order-service pod, which holds the token:

```bash
kubectl -n ecommerce-dev exec deploy/order-service -- node -e "fetch('http://product-service.ecommerce-dev.svc.cluster.local/internal/stock/p-1012',{method:'PUT',headers:{'Content-Type':'application/json','X-Internal-Token':process.env.INTERNAL_API_TOKEN},body:JSON.stringify({quantity:19})}).then(r=>console.log(r.status))"
```

## 7. Verify

```bash
kubectl get pods -n ecommerce-dev
curl http://localhost/                 # static shell via ingress -> frontend
curl http://localhost/categories       # proxied through frontend nginx -> product-service
```

## Then: observability

The monitoring stack (Prometheus, Grafana, Loki, Tempo, OpenTelemetry) is installed with
Helm and is not checked in here. Two things in these manifests exist to support it:

- Services expose a **named** port (`name: http`). A ServiceMonitor matches the port name,
  not its number — an unnamed port is simply never scraped.
- Pods carry `prometheus.io/scrape` annotations. Note the **Prometheus Operator ignores
  these** — it uses ServiceMonitor/PodMonitor CRDs. The annotations are a Prometheus
  convention from the older non-operator setup, kept for reference.

## Continuous load (k6)

`load-testing/` runs k6 inside the cluster as an always-on Deployment. It sends weighted,
open-model traffic through the ingress (mostly browsing, some search, some logged-in
activity) and pushes its own client-side metrics into Prometheus over remote-write.

Prometheus must accept remote-write first. `enableRemoteWriteReceiver: true` is in
`monitoring/kube-prometheus-stack-values.yaml`; on an existing install:

```bash
helm upgrade kps prometheus-community/kube-prometheus-stack --version 91.5.3 -n monitoring \
  --reuse-values --set prometheus.prometheusSpec.enableRemoteWriteReceiver=true
```

Then deploy the generator and its dashboard:

```bash
kubectl apply -k kind-k8s/load-testing
kubectl apply -f kind-k8s/monitoring/dashboards/dashboard-k6-load-test.yaml
```

Grafana → **k6 load test** (`http://grafana.localhost/d/k6-load-test`). Load is tuned with
env vars, without editing the script:

```bash
kubectl set env deploy/k6-load -n load-testing RATE=3              # triple the traffic
kubectl set env deploy/k6-load -n load-testing CHECKOUT_PER_MIN=6  # turn checkout on
kubectl scale  deploy/k6-load -n load-testing --replicas=0         # pause
```

Checkout is off by default: the services keep data in per-pod memory, so with 2 replicas
an add-to-cart and the checkout after it land on different pods about half the time and
the checkout fails with "Cart is empty". See the header of `load-testing/script.js`.

## Notes

- **Tracing needs app changes.** Tempo and an OpenTelemetry Collector will run happily,
  but the services have no OpenTelemetry SDK, so nothing emits spans. Instrumenting them
  means editing `services/*/src` — outside this directory.
- **Frontend DNS.** `base/frontend/frontend-nginx-configmap.yaml` overrides the image's
  baked-in `nginx.conf`, whose resolver points at AKS's CoreDNS (`10.0.0.10`). kind's is
  `10.96.0.10`. Without the override, static files serve fine and every API call 502s.
- **Secrets are placeholders in git.** Fine here because nothing reaches a real database.
  Never carry this pattern to a cluster with real data.
